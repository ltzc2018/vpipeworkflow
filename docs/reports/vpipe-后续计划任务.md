### 两条交付路径

**路径 A：`references` 文件列表（简单）**
```json

```
优点：简单。缺点：模型自己决定各参考的几何尺寸。

**路径 B：端口路线（可控，官方示例用这个）**
```
load-image  → image-resample(1024×1024)                              → ref1
load-image  → image-resample(1024×1024)                              → ref2
load-video  ┬→ video-to-rgb → image-resample(1344×768) → temporal-stack → ref3
            └→ audio-to-pcm(32000, stereo) → temporal-stack             → ref4
```

四个承重细节：
1. `attach_audio: [N]` —— 按**参考编号**（不是端口号）把音轨折叠到它前面那个参考上，保持 `<Video 1>` + `<Audio 1>` 配对
2. `channels: 2` —— 真正的立体声
3. `max_mb: 384` —— 124 帧 @ 1344×768 = 366 MiB，超过默认 256 MiB 会被截到 86 帧并告警
4. `reference_video_short_edge: 0` —— 参考视频保持在输出画布尺寸上，行数不翻倍（否则 14,580 → 约 2 倍）

## 任务 P2 · HyperFlow 8 步 adapter 对照实验

**优先级：高。** 权重已就位（`videorebirth/hyperflow`，2.8 GB，4/4 校验通过），只差跑对照。

### 关键认知（官方文档）
HyperFlow **不是 LoRA**，是「LoRA + 时间步 MLP 的一处结构改动」：
```
temb = emb(t) + gate * (emb_r(r) - emb(t))        gate = 0.25
```
每一步每行需要两个数 `(t, r)`。条件行（关键帧/参考帧）没有要去的地方，所以那里 `r == t`。

### 接线（只需改两处）
```json
"lora": "videorebirth/hyperflow",
"lora_scale": 1.0
```
- **不需要设置步数**。适配器文件里写明了蒸馏时的 sigma 网格（9 点、8 次前向），只要适配器生效，vpipe 就跑这个网格；图里的 `steps` 在此期间不被使用
- **Ref2VA 的图要用 `videorebirth/hyperflow-ref2va`** —— 同一个文件，在模型目录里登记了第二次。⚠️ **本机尚未注册这个别名，需补**
- `video_shift` / `audio_shift` 保持 **12 / 3**，与训练时一致。改成别的值会警告
- `lora_scale` 保持 **1.0**。设 0 是"精确回到原始模型"，可以同一份权重做 A/B；中间值是**未训练过的状态**

### 官方性能（M4 Pro 64GB，640×352×56 帧，3943 行）

| | 前向次数 | 每次前向 | 去噪 |
|---|---:|---:|---:|

| **HyperFlow** | **8** | **30.2 s** | **241 s** |

适配器让每次前向**慢 9%**。换来的是：原始模型要 15 步以上的片段，它 8 次前向完成。

> 建立**行数成本模型**：`行数 ≈ 305 × 帧数`（124→37 804，241→73 480，两次独立验证），
> 每行成本随行数上升（0.0469 → 0.0669 s/行）。
> **768p 值 3.09× 时间换 3.33× 细节**（29m34s vs 9m35s；交付尺寸细节能量 167.7 vs 50.3）。
> 零冻结帧、零纯黑帧、**尾部不劣化**（末 1/3 细节 176.1 > 首 1/3 159.5，是镜头推近不是画质退化）。
> **4 步 v1.2 适配器最划算**：13分26秒 = 8 步的 45.5%，细节 170.6 反而略高；
> 但**必须同时把 pipeline 的 `steps` 改成 4**（lightx2v 无 sampling contract，不会自动对齐）。
>
> **P3.4 四段式续接** → ⚠️ **只接得住第一处**。
> 接缝 SSIM **0.457 → 0.358 → 0.281 单调下降**（段内 p5 基线 0.956 / 0.958 / 0.963）；
> 相位相关测得第 2/3 处 **+76.02 px / −86.11 px 垂直重构跳变**，Δ亮度 **1.1 → 8.59 → 13.28**。
> 第 1 处位移 (0,0) 且补偿后 SSIM 仅 0.515 → 证明**不是几何错位，而是重新渲染的像素级纹理漂移**。
> 拼接片 496 帧 / 20.70 秒，解码零错误，但**净亮度漂移 −42 级**（114.5 → 72.1）。
> 官方提醒的「按行数平方算，四次普通生成更便宜」被实测**证实**。
>
> **P3.5 结论** → ✅ **24GB 上 768p 可行且稳**，但长视频**不要靠续接**：
> 单段 241 帧 1h21m 换来的是连贯性；续接四段换来的是三处可见跳变 + 亮度漂移。
> 推荐路线：**单段 ≤ 241 帧 + 多个独立短段各自成片**，而不是拼长片。

**优先级：中高。** 官方对 768p 有专门的 adapter 家族。

### 三条结论

1. **★ shift 规则按适配器分叉，「768p = 6.0」这条推广被推翻**
   - Ref2VA 768p：**12.0 更锐**（裁切纹理 178.7 vs 153.1 = +16.7%；颗粒几乎不变 1.102 vs 1.097；
     纹理/噪点 162.1 vs 139.5）→ 不是「噪点当细节」的假象
   - FL2VA 768p（第 8 轮）：仍是 **6.0 更锐** → 两条结论同时成立，不互相推翻
   - **shift 响应是台阶不是斜坡**：6.0 与 8.0 几乎等价（运动曲线 r **0.9817**、全片细节 102.5 vs 103.0），

2. **768p 多参考「部分成立」**：身份锁 ✅ / 音轨锁 ✅（谱形 r **+0.420**，对照组是 −0.146/−0.204/−0.199）/

## 任务 P11 · YUV 4:4:4 / BT.709 口径消融（✅ 2026-11-18 完成）

### 问题

我们反复记录：**视频流直接比 ≈ 0.9736，两张都先落盘 PNG 再比 ≈ 0.9445，差约 0.03 来自 YUV 4:2:0 色度往返**。
历史所有 SSIM/PSNR 数字都建立在这个口径上。

上游现在支持 **FFV1 4:2:2 / 4:4:4 + 可选 BT.601 / BT.709** → **这 0.03 可能根本不是「固有开销」**。

### 结果（✅ 2026-11-18 完成，见报告第 18.2 节）

**结论：那 0.03 的差是「比较域」造成的测量伪影，不是编码开销。可消解的是比较域，不是像素格式。**

三段消融（脚本 `scripts/p11_caliper.py`，25.7 s，**无模型、不占 GPU**）：

| 段 | 关键数字 |
|---|---|
| ① 同一 RGB 内容 → 4 种落盘格式 | 口径 A 极差 **0.1752**（0.5796/0.6191/0.7244/0.7549）；口径 B/C 极差 **0.0003**；**\|B−C\| = 0.000000（恒等）** |
| ② 真值基准（全用 ffv1 无损编码器） | 4:4:4 **0.999977**（82.31 dB）／4:2:2 0.997014／**4:2:0 0.995417**（46.67 dB）／全默认链 0.984282（41.58 dB）；自检 1.000000 |
| ③ 复现历史对 | `pika-i2va-shop` A=0.5774 vs B=0.3895（**+0.1879**）；`p4-i2va-preview-fast` A=0.3453 vs B=0.1735（**+0.1718**） |

**机制（ffmpeg `-v verbose` 直接读到）**：口径 A 下**参考 PNG 被 auto_scale 到视频的像素格式**才参与比较 ——
`rgb24/gbr/pc → yuv420p/smpte170m/tv`（4:2:0 视频）或 `→ yuv444p/bt709/pc`（4:4:4 视频）
→ 口径 A 的分数混进了「参考图被降采样的程度」，**不是一个纯粹的相似度度量**。

**三个量化判据**：
1. 口径 B（落盘 PNG 再比）**≡** 口径 C（强制 gbrp 域直比）——都是纯 RGB 域比较，读数与像素格式无关（极差 0.0003）
2. **4:2:0 只丢 0.0046 SSIM**；真正吃掉 0.015 的是 `limited range` + `bt601` + `h264 有损压缩` 三条叠加
3. **口径 A 恒高于口径 B**（+0.17~0.19）→ **第 15.4.2 节括号那句「PNG 再比会高约 0.03」方向写反了**；
   第 17.3 节 / 18.1 节的「PNG 再比偏低」表述正确（历史正文按 SOP 不改写，仅在 18.2 节标注修订）

**历史表安全性**：抽查第 16/17 节全部关键表被测文件，
像素格式**全部一致**（`h264 / yuv420p(tv, smpte170m)`）→ **历史结论不受影响**。

**新增测量纪律**：**跨像素格式比较必须用口径 B/C，或先统一转码**，否则结论无效。

### 步骤（已完成）

1. ✅ 同一段成片，分别以 4:2:0 / 4:2:2 / 4:4:4 编码，各测三口径 → 得到「格式 → 口径 → SSIM」对照表
2. ✅ 真值基准（全部 ffv1 无损）→ 分离「色度抽样损失」与「range/colorspace/有损压缩损失」
3. ✅ 复核历史表安全性 + 判定报告内部方向性矛盾 + LFM3-VL 第三方复核（`scripts/vqa-p11.sh`）

### 风险（已消解）

- ~~依赖 P12（需要新版 FFV1 参数）~~ → **证伪：已装 App（`9db5dd7`）就已支持 `yuv444p`/`full`/`bt709`/`ffv1`/`alac`**，
  实跑转码 797 ms 验证通过；第 16 节续接流水线早就在用官方 lossless 配方
- ~~历史实验视频多数是 4:2:0 存的~~ → ✅ 已复核：历史表**同格式**，组间可比性未受影响

### 衍生结论（生产链建议）

交付片建议 `yuv444p + full + bt709 + ffv1`（或至少 `full + bt709`），
相对默认链（`yuv420p + limited + bt601 + h264`）**可回收约 0.011 SSIM**。

## 任务 P13 · 复现 #55「纹理沸腾」（🟡 2026-11-17 新增）
