## 1. 轮次编号与并发保护

1. 读 `.auto-round-state.json`（不存在就创建 `{"round":0,"last_run":null}`）→ 本轮 `R = round + 1`。
2. **互斥**：若 `.auto-round.lock` 存在且 mtime 距今 < 90 分钟 → 说明上一轮还在跑，**本轮直接跳过**，在报告里写「上一轮未结束，本轮跳过」，不要两个轮次并发。
3. 拿到锁：写 `.auto-round.lock`（内容 = 本轮时间戳）。
4. 本轮**成功结束后**写回 `{"round": R, "last_run": "<本轮时间>"}` 并删除 `.auto-round.lock`。
   失败也要删锁，但不要递增 `round`（下一轮可重试同一 R）。

- 每轮最多 1 个实验任务；**重任务串行**（实测并行会互相杀死进程）。

- 后台跑重任务用 `setsid` + `.done` 幂等 + PID 续接（模板：`vpipe-lab/scripts/p9_runner.sh`、`p3_runner.sh`、`p3_chain.sh`），

- 每个生成任务结束后**必须抽帧目检**：ffmpeg 抽第 0/40/80/末帧拼印相 + LFM3-VL 复核
  （流水线 `vpipe-lab/pipelines/lfm3-vl-vqa.vpipeline`，批处理模板 `vpipe-lab/vqa-round4.sh`）。
- **每个结论都要有量化证据**：SSIM/PSNR（`vpipe-lab/anchor-fidelity.sh`）+ 第三方模型复核。**只看日志不算数**。
- **量化口径必须注明**：视频流直接比

  比「两张都先落盘 PNG 再比」高约 0.03（YUV 4:2:0 色度往返损失）。**两种口径不要混用**。

## 6. GitHub 同步（每轮结束前）

### 6.1 用常驻工作副本，不要每轮全量 clone（★ 2026-11-17 实测）

仓库 `ltzc2018/vpipeworkflow` 的 `size` 是 **216,872 KB ≈ 212 MB**（41 个视频占大头）。
**全量 `git clone` 会被 SIGTERM 打死**（退出码 137），沙箱内外都复现。

**正确做法**：常驻副本 + 增量 pull。

```bash
REPO=/Users/minichen/WorkBuddy/2026-11-12-21-10-11/.vpipeworkflow

# 首次（只需做一次；后台跑，别用前台，会超时）
git clone git@github.com:ltzc2018/vpipeworkflow.git "$REPO"

# 每轮
git -C "$REPO" pull --ff-only
```

**不要用 `--filter=blob:none` 部分克隆做同步**：
`git ls-tree -l`、`git checkout` 会为**每个缺失 blob 单独回源**（本仓库 395 个文件 = 395 次往返）→ 同样被打死。
部分克隆只能当**只读探测工具**（例如看远端文件树）。

### 6.2 每轮同步的内容

```bash
cd "$REPO"
# 复制本轮新增/变更的：
#   skills/    技能包（含 references/）
#   scripts/   脚本
#   pipelines/ 流水线
#   docs/reports/  两份主报告 + SOP + daily-knowledge + 轮次状态
git add -A
git commit -m "docs: 第 R 轮夜间知识同步（YYYY-MM-DD HH:MM）"
git push origin main
```

- **仓库内路径必须相对化**（相对 vpipe 工作目录），仓库自带 `refs/` 参考图。
- **⚠️ 真人素材一律不入 public 仓库**：`refs-real/`、`*real-photo*`、`*boogu-real*` 绝不 push。
- push 后用 GitHub API 复查**真人文件数为 0**。
- 视频产物若本轮有新增，用 `git add` 单个文件即可（按需拉取那一个 blob，不会全量回源）。

## 8. 已知坑清单（避免重复踩）

### 接线 / 参数
- 参考生视频与首帧锚定**互斥**；商品要全程在场必须用首尾帧锚定。
- 仅首帧锚定时主体会在第 20–40 帧之间消失。
- `save-video` 的键是 `output_url` 不是 `path`，且必须接两路输入（rgb-to-video + audio-vae-decode）。
- `video-ref-encoder` 与 `generate-video` 的 `frames` 必须相等，否则整个请求被跳过。
- `model_variant` 逐字段比对 `version`/`variant`/`name`/`model_type`，用 `model_type` 最稳。
- 官方多参考上限：9 图 + 3 视频 + 3 音频 = 12 项，单段参考视频 2–15 秒，总时长 ≤ 15 秒。
  - `attach_audio` 的数字是「**音频那条参考自己的槽位号**」（1 起算）→ ≥4 条参考时才暴露歧义。
  - **没用到的参考端口不要接** —— 一个空端口会重编号后面的所有参考。
- 引导长度必须是 `17n+5` 帧（90 = 17×5+5）。

### 模型 / 采样
- **shift 规则按适配器分叉，不是按分辨率**：
  FL2VA 768p = 6.0 更锐；**Ref2VA 768p 实测 12.0 更锐**；544p / Pika / HyperFlow = 12.0。
- **shift 响应是台阶不是斜坡**：6.0 与 8.0 几乎等价（运动曲线 r 0.9817）→ 中间值不必试。
- **shift 写错完全静默**：只有 HyperFlow 与带 `sampling_contract` 的适配器才 warn（`stages/generate-video-stage.cc:3746`）。
- **4 步适配器必须同时把 pipeline `steps` 改成 4**，否则静默劣化。
- **HyperFlow 是 flow-map adapter 不是普通 LoRA**；`lora_scale: 0` 精确回到原始模型（已三组验证）；Ref2VA 注册名 `videorebirth/hyperflow-ref2va`；适配器生效时 `steps` 被忽略。
- **Boogu 图生图**：参考图走 Qwen3-VL 语义条件**不走 latent**（不需要 `vae-encode`）；调度器必须 `boogu_v1`；CFG 固定 1；**每张参考图各接一个 `image-resample`**；参考图必须预裁成单一主体。
- 本机 HuggingFace 直连不通，**全部走 ModelScope**（`VPIPE_MODEL_SOURCE=modelscope`）。

### 度量 / 复核
- **细节能量会把噪点当细节** → 评价锐度必须同时看「3×3 中值滤波后纹理量」与「颗粒量」。
- **接缝判据必须用相位相关**（区分「几何错位」与「重新渲染纹理漂移」）；**不能只靠 LFM3-VL 读图**（它把 76px 重构误读为「自然姿态变化」）。
- **LFM3-VL-2B 三个缺陷**：否定式问题编答案；分不清细微锐度差；**运镜方向判断不可靠** → 运镜只信相位相关。
- 768p 多参考只一半成立：身份锁 ✅ / 音轨锁 ✅ / **运镜锁 ❌**；代价：行数 ×2.10、耗时 ×3.64、画质 −17%。

### 预览 / 续接
- **TAE 实时预览**：`preview` 是 WebSocket sink，**CLI 下流水线永不结束**；必须接 `generate-video` 的 **oport 2**（接 oport 0 静默失效）；预览流有**两个 init 段**要分段拼装；各拍**相位不对齐**，横向比较前必须相位对齐（否则 0.13 vs 0.93）。
- **锚定涌现**：有锚定 step1 SSIM 0.9534；无锚定 step1 0.7085、step3 才收敛 → 锚定后第 1 步预览就能判断商品有没有跑偏。
- **官方四段式续接**：`temporal-slice(start=-90)` + `audio-to-pcm(start_s=段长-3.75, duration_s=3.75)` + `video-ref-encoder(attach_audio=[2])` + ffv1/alac。

### 环境 / 脚本
- **后台任务被回收会 SIGHUP 杀掉重任务** → `setsid` + `.done` 幂等 + PID 续接 + 内存/磁盘门限。
- bash 3.2 **无 `declare -A`** → 用 `case` 分派。
- 数组追加 `files+=(-i "$f")` 是**两个元素** → 图像计数用独立计数器。
- **`$N` 后紧跟中文全角标点会被吞进变量名** → 一律 `${N}`。
- ffmpeg `ssim` stats **索引 1 是 Y 分量** → 按 key 解析 `All:`。
- `os.rmdir` / `rm -rf` 被 sandbox 拒；`ps`/`top` 被封禁 → 用 `.mem` 采样 + PID 文件。
- Bash 工具 timeout 上限 600000 ms → sleep 分段 ≤ 9 分钟。

## 9. 调度器实现说明（2026-11-17 实测）

- `FREQ=DAILY` **不支持** 多值 `BYHOUR`（校验直接拒绝：`BYHOUR must be an integer between 0 and 23`）。
- `FREQ=HOURLY;INTERVAL=2;BYMINUTE=30;BYHOUR=0,2,4,6` **会忽略 BYHOUR 与 BYMINUTE**：
  实测 nextRun = 创建时间 + 2h（20:34 → 22:34），与指定小时无关。
- **因此本系列用 4 个 `FREQ=DAILY` 单时段自动化实现**：00:30 / 02:30 / 04:30 / 06:30。
- 4 个自动化共用本 SOP，靠 `.auto-round-state.json` 递增轮次 + `.auto-round.lock` 防并发。

## 10. 2026-11-18 第 3 轮补充的坑与纪律（★ 优先于上面的旧条目）

### 10.1 ★★★ 已装 App **不是** seed 可复现的 —— 所有同 seed 对照必须先测漂移基线

- 同一个流水线、同一个 seed、同一台机器**连跑两次**：**0/22 帧逐位相同**，整段 **SSIM 仅 0.750072**，
  文件大小都不同（245 549 B vs 244 535 B）。
- 原因：上游 bit-for-bit 修复 `e6972ac`（2026-11-06）**晚于**已装 App（`9db5dd7`，2026-11-01）；本地源码树 `33cda00` 已含。
- **实测漂移幅度**：sharpness **8.7%**、HF jitter **18.4%**、frame diff **22.4%**、static_hf_jitter **13.5%**。
- **纪律**：任何组间差异**必须先跑一次同配置重复运行**拿到漂移基线，效应超过基线才可采信。
- **不要用 mp4 文件哈希判断两次生成是否一致**（容器含时间戳）→ 比 **`framemd5`** 与**音频轨 md5**。

### 10.2 ★★ 旧 build 会**静默丢弃**新 config 键

- 在已装 App 上给 `minimax-h3-model-config` 写 `sigmas`：零报错、零告警、**零日志回显**，
  输出与不写该字段**逐位相同**。
- 这是「shift 写错完全静默」的升级版：**字段根本不存在时也是静默的**。
- **纪律**：写完新字段，**必须在日志里找到它自己的回显**（例如 `the video's 8 steps on sigmas [...]`）。
- 推论：「已装 App 有这个能力」**不能**从「源码里有」推断出来，得逐字段验。

### 10.3 ★★ 换 `video_shift` = 换场景

- 只改 `video_shift`（其余全同）时首帧 SSIM 仅 **0.46–0.56**；
  即便用静图参考 + 完全静止提示词也一样（**0.5062**）。
- **纪律**：跨 shift 的结论只能表述为「两条不同 σ 网格的对比」，不能表述为「同一模型渲染得更锐」。

### 10.4 ★★ 上游官方文档的 shift 表是权威来源（别只靠社区表）

- `docs/MINIMAX-H3.md`（源码树自带）有完整的**适配器→partition→steps→shift** 表，
  关键三条：768p 家族蒸馏在 **shift 6**；**Ref2VA 8-step 768p → 6.0**（唯一需要 6.0 的 Ref2VA 适配器）；

- **纪律**：查 shift 先查上游文档，再查社区表（sdnext 的表与上游逐行一致，可作交叉印证）。

### 10.5 ★ 不碰已装 App 也能跑本地 build（symlink farm）

### 10.6 ★ 编辑正在运行的 bash 脚本会破坏它的执行

- bash 按**文件偏移增量**读取脚本，中途改文件 → 从错位处继续读 → 本轮把 `p13_runner.sh` 的 `case`
  读成了 `*)` 分支 → `exit 2`。
- **纪律**：**改调度脚本前先停掉正在跑的实例**。

- 多一个空 iport 会把 `minimax-h3-model-config` 挤到下一槽位 →

  （producer `TensorBeatPayload` vs consumer `FlexDataPayload`）。
- **纪律**：改流水线时**照抄模板的 iports 列表**，别凭印象重排。

### 10.8 LFM3-VL-2B 的第 4 个缺陷（本轮发现）

- 问「这三张是不是同一个场景？」它答「**完全相同**」，而定量首帧 SSIM 只有 0.51–0.56。
- → 它按**语义层**（主体/背景/光线）判断场景同一性，**对像素级场景差异不敏感**。
- **纪律**：**「是否同一场景」只能靠首帧 SSIM / 相位相关裁决，不能靠 LFM3-VL。**
  （它仍能可靠回答「有没有运动」这类粗判 —— 本轮用它确认了静态夹具成立。）

### 10.9 磁盘受限时怎么设计实验

- 本轮磁盘仅 **5.1 GiB**（远低于 15 GiB 下限）→ 刻意选「**模型已在本地、只跑短片**」：
  22 帧 / 1344×768 / 8 步，**每臂 3 分 55 秒、产物仅 240 KB** → 三臂 + 一次重复运行全部完成。
- **规律**：短片（22 帧 = 17×1+5）+ 本地已有模型 + 单臂 < 4 分钟 ≈ 可在低磁盘下做完整对照。

### 10.10 ★★★ GitHub 同步脚本的 `cp -R` 尾斜杠缺陷（已修，第 3 轮发现）

- **BSD/macOS 的 `cp -R src/ dst/` 是「把 src 的*内容*铺到 dst」**，不是「把 src 这个目录搬进 dst」。
- 旧写法 `cp -R "$d" "$REPO/skills/"`（`$d` 带尾斜杠）→ 每个技能的内容被**平铺**到仓库 `skills/` 顶层：
  `skills/SKILL.md`、`skills/references/`、`skills/assets/`、`skills/scripts/`。
- **后果（实测）**：
  1. 正确定位的 `skills/<name>/…` **从此再也没被刷新** —— 实测陈旧了整整两轮
     （`vpipe-model-prepare/references/768p-adapters.md`：仓库 21 603 B vs 源 36 163 B）；
  2. `skills/SKILL.md` 被**最后一个技能覆盖**（实测 = `vpipe-text-to-image`）→ public 仓库里误导读者；
  3. 内容只靠平铺副本才进了仓库 → 仓库里长期存在两套漂移的技能副本。
- **修法**（已改 `scripts/nightly_sync.sh`）：显式指定目标目录
  ```bash
  mkdir -p "$REPO/skills/$name"
  cp -R "$d" "$REPO/skills/$name/"      # ← 目标带斜杠 = 内容进该技能目录
  ```
- **配套清理**：删掉仓库顶层的 `skills/{references,assets,scripts}/` 与 `skills/SKILL.md`
  （已逐文件核对：全部在 `skills/<name>/…` 有副本，0 个独有文件）。
- **验收口径**：同步后必须逐个比对「仓库 `skills/<name>/references/X`」与「实验室 `skills/<name>/references/X`」的字节数，
  **不能只看树里有这个文件**。
- **通用教训**：BSD 与 GNU 的 `cp` 在尾斜杠上语义不同；**跨机器写同步脚本时，先用 `cp -R src/ dst/` 实测一次**。

## 11. 2026-11-18 第 3 轮续作（P15）补充的坑与纪律（★ 优先于上面的旧条目）

### 11.1 ★★★ 「不可复现」先查开关，不要先怪版本

- 上游 bit-for-bit 不是「升级到某个 commit 就自动生效」，而是**一个需要显式打开的开关**：
  `autotune: false`（三个 stage：`generate-video` + `vae-decode` + `video-ref-encoder`）
  + （M4 Pro 上）钉死 `ane_rows`。
- **本机实测**：已装 App（`9db5dd7`）与本地 build（`33cda00`）同配置输出**逐位完全相同**
  → **版本新旧与不可复现无关**；本地 build 默认 `autotune=true`，**同样不可复现**。
- **纪律**：任何「同 seed 跑两次不一样」的观察，先去上游 commit 全文里找**开关**，
  再下「版本旧」的结论。第 3 轮就因为先怪版本而错了一次（修订编号 R3-1）。

### 11.2 ★★ 关掉竞速不是「牺牲性能换确定性」，本机反而更快

- 实测：`autotune` 开 225 s / 关 **220 s**（**−2.2%**）。
- 原因在日志里：`[h3-dit] first forward at 9294 rows: 4710 ms before block 0 (… gemm autotune 4635 …)`
  → **首帧前向的 4710 ms 里 4635 ms（98.4%）花在内核竞速上**。
- **纪律**：看到日志里的 `gemm autotune ####` 毫秒数，就要想到两件事：
  ① 它是**不可复现的来源**；② 它是**可以省掉的开销**。

### 11.3 ★★ `framemd5` 全流会混进音频包

- `ffmpeg -f framemd5` 默认把**所有流**都写进清单 → 本片 22 帧片的清单是 **51 行**
  （22 视频帧 + 29 音频包），第三列是 packet 序号/大小。
- **纪律**：做逐帧判据**必须 `-map 0:v`**，否则帧数口径会被误读成 51 帧。

### 11.4 ★★ 逐位判据的完整组合

`framemd5`（视频流） + **音频轨解码后 md5** + SSIM（双口径）+ PSNR。
**绝不能用 mp4 文件哈希**（容器含时间戳，字节必不同）。

### 11.5 ★ 竞速漂移是「纯细节噪声」，与「换 shift = 换场景」是两种机制

- 只差竞速的两次运行：**同一场景、同一语义**，仅像素细节不同（sharpness 9.1% / HF jitter 20.3% /
  frame diff 25.2% / static_hf_jitter 14.5%）。
- 而只改 `video_shift` 会**换掉整个场景**（首帧 SSIM 0.46–0.56）。
- **纪律**：这两件事不可互相解释；做 shift 对照前**先关竞速**，把混淆项拆开。

### 11.6 ★ 漂移基线可跨 build 复用

第 3 轮在 App 上测到的 8.7% / 18.4% / 22.4% / 13.5%，在本轮本地 build 上复现为
9.1% / 20.3% / 25.2% / 14.5% → **漂移基线与二进制版本无关，是本机硬件/模型的属性**。

### 11.7 ★ `image-resample` 的 `fit: stretch` 是唯一破坏长宽比的模式

- 枚举：`pad`（保长边+填充）/ `crop`（保短边+中心裁）/ **`stretch`（改长宽比）** / `manual` /
  `pad_to_grid` / `crop_to_grid` / `crop_to_area`。
- **纪律**：参考图**非正方形**时不要用 `stretch`；lightx2v 官方推荐 `match`
  （面积匹配、保比例、**不上采样**），vpipe 侧对应 `pad`。
- 另：`reference_image_short_edge` 默认 **2048（Ref2VA）/ 768（FL2VA）**，
  2048 → **121 个 VAE tile**，1024 → 25 个；上游自己的示例用 1024。

### 11.8 ★ 本地源码树可能是 squash 过的

- 本机 `repo/vpipe` 只有 **1 个 commit**（`33cda00`）→ **无法用 `git log` 找 `e6972ac`**。
- **纪律**：squash 的源码树里**日期是唯一可靠的时间线**；找某个 commit 的内容要走上游 API + commit 全文。

### 11.9 ★ 上游 issue 可能长期零回应

- #55（纹理沸腾）：`open` / **0 条评论** / 最后更新 2026-10-21 → **开放 28 天零回应**。
- **纪律**：本实验室的自查能力（逐位判据 + σ 网格公式）要继续自建，
  **不要把结论押在上游回应上**。

### 11.10 ★ 续作不占轮次编号

## 13. 2026-11-18 第 5 轮补充的坑与纪律（★ 优先于上面的旧条目）

### 13.1 ★★★ 「看起来像效应」的数，只有漂移 = 0 才可采信 —— **而且压到 0 之后它可能是反的**

- 第 3 轮测得「`er_sde` σ 网格让 HF jitter **−16%**」，当时正确地没下结论（落在 18.4 % 漂移带内）。
- 第 5 轮在 `autotune: false`（漂移 = 0）下重测 5 臂 → **HF jitter 变成 +12.09 %**，**符号相反**。
- ⇒ **纪律**：任何「效应量」在漂移基线压到 0 之前**一律不许写成结论**；
  压到 0 之后要**重新核对方向**，不能默认「之前的方向是对的」。
- ⇒ **推广**：**「当时没下结论」本身就是正确动作**；反过来，
  **「看起来效应量很大就写进结论」是本实验室最危险的失误模式**。

### 13.2 ★★ 跨轮次锚点是最强的可复现性证据

- 本轮 B 臂（默认网格）与**第 4 轮**的 `p18-euler.mp4` **逐位相同**
  （framemd5 同 / 音频 md5 同 / SSIM 1.000000 / PSNR inf / **字节 244 535 = 244 535**）。
- ⇒ 默认网格臂的产物在**第 3、4、5 三轮**之间逐位相同
  （跨轮次 + 跨二进制版本 + 跨 sampler 接线方式）。
- ⇒ **纪律**：每轮实验都要留一个**能与历史产物逐位对拍的锚点臂**，
  它同时验证「本轮流水线没写错」和「历史结论仍成立」。

### 13.3 ★★★ 「生态刚出」与「本机装不下」是两件事 —— **先扫树再下结论**

- 本轮 H3-Image：**vpipe 其实早已完整支持**（上游 6 条官方流水线，含 fast-M5 版；本地树 106 个文件命中），
  只是 `prepare-minimax-h3-image.vpipeline` 拉 **≈135 GB** 权重 → **本机不可行**。
- 若只搜社区，很容易写成「生态刚出、vpipe 还没适配」→ **结论方向完全错**，
  而且会白跑一次 135 GB 下载。
- ⇒ **纪律**（扩展第 4 轮 12.1）：
  1. 「生态有 / vpipe 无」→ **写上游 issue**；
  2. 「vpipe 有 / 本机装不下」→ **写可行性否决 + 省下下载**；
  3. 两者的**证据形态完全不同**（前者是树扫描 0 命中，后者是体积核算），
     **必须分开写，不能混成一句「做不了」**。

### 13.4 ★★ 检索清单要加「上游组织/用户的全部仓库」

- 本轮用 `api.github.com/users/tgo-app-dev/repos`（而不是 `repos/tgo-app-dev/vpipe`）
  才发现 **`valtz`**（79 stars），而它**内置 MiniMax 官方的 H3 提示词技能** ——
  这是本轮最高价值的一条知识，**只盯主仓库是找不到的**。
- ⇒ **每轮固定检索项**加两条：`users/{owner}/repos` 与 `orgs/{org}/repos`。

### 13.5 ★ 模型体积必须逐文件累加（第 4 轮 12.7 的第 N 次印证）

- 本轮逐文件实测：FlashVSR 原生 **6.95 GB**（第 4 轮记 6.48）、MLX 档 **3.51 GB**（第 4 轮记 3.27），
  **都偏小 0.24–0.47 GB**；社区博客把 ControlNet Union 写成「约 13.5 GB」（实测 2.30–8.38 GB）。
- ⇒ **纪律**：**永远不用「仓库总大小」或博客聚合数**；
  一律 `ModelScope API` 逐文件取 `Size` 后累加。

### 13.6 ★ 参考标签写错 = 静默失效（新的静默坑）

- 上游原文：**「an unmatched tag is ordinary text to the model」**，**nothing reports it**。
- 且 `<Picture i>` / `<Video k>` / `<Audio j>` **计数器各从 1 起算**（不是按列表位置）。
- ⇒ **静默失效清单**（第 3 轮 10.3 + 第 3 轮续作 11.1/11.2 + 本条）：
  `shift` 写错 / `autotune` 竞速 / 旧 build 丢字段 / **参考标签写错**。
- ⇒ **纪律**：凡是「引用了但模型没吃进去」的现象，**先怀疑标签，再怀疑模型**。

### 13.7 ★ 生成器必须带自检断言

- 本轮 `make_p13b_pipelines.py` 里我一开始把「`generate-video` 的 iport 3」写成「`oport==3`」，
  **断言直接 `IndexError` 退出**（而不是生成一个坏流水线去跑 20 分钟）。
- ⇒ **纪律**：流水线生成器在写文件前必须断言：
  ① `autotune:false` 的处数；② `iports[N]` 的 src；③ `iports` 总项数；④ 两臂的 `config` 差异集合。
  **断言失败要早、要响**。

### 13.8 ★ 同名不同物要单独建条目

- `dmd`（**vpipe 采样器**，推理期换 σ 轨迹）与 **DMD2（FastH3 蒸馏模型**，训练期改权重）
  名字相近、社区常混用 → 本轮在 `sampler-spec.md` 建了对照表。
- ⇒ **纪律**：读到社区帖里的模型/方法名，先问「它是权重还是采样器？是训练期还是推理期？」。

### 13.9 ★ 换 σ 网格 = 换轨迹（第 3 轮 10.3 / 第 4 轮 12.3 的第三种）

- 本轮 A 臂（`er_sde` σ 网格）vs B 臂（默认网格）首帧 SSIM **0.604196**。
- ⇒ 与「换 shift = 换场景」（0.46–0.56）、「换采样器 = 换场景」（0.44）**同族**。
- ⇒ **纪律**：跨 σ 网格的结论只能表述为「**两条不同轨迹的对比**」，
  **不能**表述为「同一场景的画质对比」。

### 13.10 ★★ 闭式公式要拿「运行时真值」验证，不只是拿文档互验

- 本轮 A 臂日志回显了**运行时实际使用的音频 σ 串**，
  与 `scripts/p15_sigma_grid.py` 闭式公式 **9/9 逐值吻合（4 位小数）**，
  其中 0.3819 / 0.1344 两个值只有「反解 q 再过 `audio_shift`」才能算出来。
- ⇒ **纪律**：凡是本实验室自己推的公式，
  **证据分三级**：文档级双源互验 → **运行时真值** → 跨实现印证。
  **写进结论时必须注明当前处于哪一级。**

### 13.11 ★ 磁盘受限时怎么设计实验（第 3/4 轮规律的第三次验证）

- 本轮磁盘 **5.3 GiB**（< 15 GiB 下限）→ 仍然能跑完 **5 臂**（每臂 3m39s、产物 240 KB）。
- ⇒ **规律（已连续三轮成立）**：
  **模型全在本地 + 22 帧短片（17n+5）+ 单臂 < 4 分钟 + 产物 < 300 KB** ≈ 可在低磁盘下做完整对照。
- ⇒ **配套**：**跨轮锚点臂要留**（本轮靠它一次证明了「漂移 = 0」与「第 3/4/5 轮一致」）。

## 14. 2026-11-18 第 6 轮补充的坑与纪律（★ 优先于上面的旧条目）

### 14.1 ★★★ 「看起来像失真」也可能是效应 —— 评价 AI 超分必须双口径

- 同一对片：SSIM 判 FlashVSR「比纯插值差 0.0506 / 4.05 dB」，**纹理量判它「好 12.6×」**。
- ⇒ **纪律**：凡是「生成式」处理（超分 / 修复 / 补帧 / 放大），
  **必须同时报「保真口径」（SSIM/PSNR）与「细节口径」（中值滤波后纹理量 + 颗粒量）**，
  只报一个都会得出反向结论。
- 这是第 3 轮坑「细节能量会把噪点当细节」的**姊妹坑**：
  那一条是「把噪点算成细节」，这一条是「**把真细节算成失真**」。

### 14.2 ★★ 复现性判据必须**分家族**，不能跨家族外推

- H3：`autotune:false` → **逐位相同**（framemd5 同）。
- FlashVSR：同样写 `autotune:false` → **framemd5 不同**，但**指标漂移 ≈ 0**。
- 原因：**flashvsr 家族的 sampler / scheduler / negative port 全部惰性**
  （`one step at a fixed timestep`，guidance 已蒸馏）→ **`autotune` 没有可调对象**
  → **日志里连回显都没有**（符合第 3 轮坑 10.2 的「字段没被消费 = 静默丢弃」）。
- ⇒ **纪律**：每个新家族第一次跑，先问「**这个家族有没有 sampler/scheduler？**」
  没有 → 复现性只能用「**framemd5 + 指标漂移**」双判据，别拿 H3 的 bit-for-bit 预期去套。

### 14.3 ★★★ 磁盘回血要立刻变现（清盘比再搜知识值钱）

- 本轮磁盘从 5.3 GiB 回升到 **32 GiB** → **立刻**解锁拖了 3 轮的 P22（6.953 GB 权重）。
- ⇒ **纪律**：每轮开跑前先 `df -h`；**磁盘一旦过 15 GiB，立刻把看板里因磁盘被阻塞的最高优先级任务捡起来**，
  不要继续搜知识（第 4 轮 12.8 的判断在本轮兑现）。

### 14.4 ★★ 新 stage 的「几何契约」先查源码，别照抄官方模板的分辨率

- 上游 `flashvsr-family.h` 明写：**输出宽高必须 128 的倍数；帧数必须 8k+1（v1.1 单 clip ≥25）；
  输出 = 4× 源片**。
- 官方模板用 1920×1152，**那是 8×B200 级别的配置**；
  本机 24 GB 按上游给的内存账（~20 GB @1920×1152）**根本跑不了**。
- ⇒ **纪律**：新 stage 的官方模板只提供**接线形状**，**分辨率与帧数必须按本机内存账重算**。
  读源码里的内存数字（`continuity:auto` 的判据、`kv_ratio` 的携带量）比读 README 靠谱。

### 14.5 ★★ `group_size` 大于帧数 = 挂住，不是报错

- `temporal-stack` 的 `group_size` 是「攒够才发 beat」→ **永远攒不够就一个 beat 都不发**，
  流水线**静默挂住**（不是报错、不是崩溃）。
- ⇒ **纪律**：凡是 `group_size` / `clip_frames` 类的「攒批」参数，
  **必须写断言 `group_size ≤ 实际帧数`**（本轮写进 `make_p22_pipeline.py` 的自检）。

### 14.6 ★★ 日志里的 `[WARN]` 要看**后面跟了什么**

- 本轮 VAE 解码先报 `[WARN] the stream's decode failed (insufficient free RAM …)`，
  紧接着 `[NORMAL] MetalWanVae: 1280x768 decode runs TILE-OUTER … 3x4 tiles` →
  **那是自动降级成功，结果是对的**。
- ⇒ **纪律**：判定失败要看「**有没有后续的成功行**」，不要看到 WARN 就判负。

### 14.7 ★ 未注册的模型名可以直接当路径用

- `resolve_model()` 对 registry 里没有的 ref **原样返回** → `hf_dir` 写**绝对路径**即可，
  不必写 LMDB 条目。
- 但：**目录里有且仅有一个 `.safetensors`**（`resolve_adapter_file`：「several are not」——
  目录遍历顺序不是任何人做的选择）。
- ⇒ **纪律**：手工放权重的目录，先 `ls *.safetensors | wc -l` 确认只有一个。

### 14.8 ★ 编码器要求偶数宽高

- `libx264` 直接拒 320×183：`height not divisible by 2`。
- ⇒ **纪律**：任何要进 h264 的尺寸都取偶；FFV1/mkv 则无所谓（可保留奇数高）。

### 14.9 ★ 本机没有 `ffprobe`

- `~/.hermes/tools/ffmpeg-9.0.1-darwin-arm64/` **只有 `ffmpeg`**。
- ⇒ **纪律**：尺寸/帧数一律用 `ffmpeg -i` 的 stderr 正则解析（本实验室脚本一贯如此）。

### 14.10 ★ HF API 可能被沙箱拦（本轮实测）

- 本轮 `api.huggingface.co` 的 `api/models/…`、`api/spaces/…` 三个端点**全部返回非 JSON**。
- ⇒ **纪律**：**HF 侧的状态类结论（模型更新、Space 是否还在、讨论区新评论）不要只靠 API**，
  必须有**第二条路径**（WebFetch / 搜索侧索引）；本轮据此把「P25 的 Space 仍在」降级为
  「**本轮未直连复核**」，**不写成已确认**。

### 14.11 ★★★ 本轮的一条正向经验：「生态有 / vpipe 有 / 本机跑得动」要再加第四种形态

- 本轮确认 **MiniMax H3 Max = fal.ai 托管，权重未开源** →
  它不是「生态没有」，而是「**生态有，但只有托管形态**」。
- ⇒ **纪律**：判断一个生态能力时，**「有没有权重」和「权重是不是开源」是两问**。
  本地能跑的永远是第二问的交集。

### 14.12 ★★★ 第 6 轮发现：**第 10.10 节的「正解」在本沙箱里是错的**（`cp` 尾斜杠语义被反转）

- 第 10.10 节写的正解是「源带斜杠 + 目标带斜杠」：`cp -R "$d" "$REPO/skills/$name/"`。
  **本机 `cp` 走 sandbox shim，尾斜杠语义与 BSD 相反**（第 6 轮三个用例实测）：

  | 写法 | 实际结果 |
  |---|---|
  | `cp -R src/  dst/` | `dst/src/…` ← **仍然嵌套**（源带斜杠被忽略） |
  | **`cp -R src/. dst/`** | **`dst/…`** ← ★ **唯一正确的「铺内容」写法** |
  | `cp -R src   dst/` | `dst/src/…` ← 嵌套 |

- ⇒ **第 6 轮用旧写法，重新制造了嵌套副本 `skills/<name>/<name>/…`（21 个条目入库）**，
  而正确定位 `skills/<name>/references/…` **仍是旧内容** → 出现
  「**树里有这个文件，但内容陈旧**」的经典静默失败。
- ⇒ **修法（已落地 `scripts/nightly_sync.sh`）**：
  1. 复制改成 **`cp -R "$d." "$REPO/skills/$name/"`**（源带 `/.`）；
  2. 复制后**自动清理** `skills/<name>/<name>/…` 嵌套副本；
  3. **逐文件比字节数**，任一不一致就 `fail` 中止推送（不再靠人眼验收）。
- ⇒ **通用教训（比第 10.10 节更强）**：
  **同一台机器、同一个命令，语义可能因执行环境（沙箱 shim / 容器 / 远程）而变**。
  所以「跨机器写同步脚本时先实测一次」还不够 ——
  **要「每次复制后逐文件比字节数」把校验内置进脚本**，而不是把校验留给 SOP 的人工条款。
